Why this matters in plain English — 3 things

1. Multi-tenant safety (OCT-46 / 47 / 48 / 49). Until this week, every report that summed money — P&L, campaign performance, the unified report — pulled from every tenant's data in the same database. Single-tenant in prod today, so no visible bug. But the moment you onboard a second business in Stato, the dashboards would have silently mixed the two. Now there are explicit WHERE business_id = ? guards on every aggregation path, with regression tests that seed an "alien tenant" and verify your owner view never sees their numbers.

2. Xero rate-limit resilience (OCT-51 / 54). When Xero throttles (HTTP 429 — which you've seen on the bank widget), the previous code would retry with exponential backoff and could hang for up to 90 seconds before giving up. With this week's changes, every Xero call has both a 15-second total budget AND a per-fetch timeout. If Xero hangs, you get the existing "rate-limited" amber banner in under 15s instead of a frozen UI.

3. Error-copy hygiene (OCT-45 / 53). When Xero rejected credentials, the integrations card used to say "verify XERO_CLIENT_ID and XERO_CLIENT_SECRET on Railway match the values in the Xero portal." Both the env-var names and the hosting platform leaked into operator UI — fine for you, but anything that ends up in a screenshot or support ticket gives outsiders a starting point on the deployment topology. New copy: "Xero rejected the credentials — verify the Custom Connection client ID and secret in the Xero developer portal match the values in the server configuration." Same info; no implementation detail. Regression test scans every source file under src/ to make sure the env-var names can never silently sneak back into UI.
